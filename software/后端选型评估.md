# DataTransTool 后端技术选型评估（Python vs C++）

> 评估对象：[软件功能设计.md](软件功能设计.md)、`data/` 下的模板/示例、[transExcelFile.py](transExcelFile.py) 原型。
>
> **结论先行：推荐 Python 做数据处理后端，Qt/C++ 只做前端壳；两者用独立进程 + JSON 契约隔离。** 不建议把 Python 嵌入 C++，也不建议用 pandas 直接 `to_excel` 交付固定模板。
>
> **2026-11-09 已确认并落地：** 输入只按 `inputExample-total.xlsx` 布局、只收 `.xlsx`；TC 的 ERP/EPR 编码留空；Eplan 的“一类产品/行业”固定 `1:电气工程`。实现与打包说明见 [README.md](README.md)。

## 1. 结论

| 方案 | 建议 | 说明 |
|---|---|---|
| **A. Qt/C++ UI + Python CLI 后端** | **首选** | 保留 Qt/C++ 界面，Excel 交给 openpyxl；进程隔离、可测试、可回退 |
| B. Qt/C++ UI + QXlsx 纯 C++ | 条件备选 | 仅当“单文件原生 exe、只支持 .xlsx、团队只写 C++”是硬约束 |
| C. PySide6 全 Python | 次选 | 如果界面语言不强制 C++，总成本最低；仍然是 Qt |
| D. Qt/C++ 嵌入 Python | 不推荐 | 打包、GIL、崩溃耦合，复杂度高于收益 |
| E. Qt/C++ + Python HTTP 服务 | 不推荐 | 对这个规模是过度设计 |

**一句话：** 这个项目的难点不在计算，而在 Excel 格式兼容、表头识别、校验和交付部署。Python 在前三项明显占优，C++ 只在部署一项占优；用“Qt 壳 + Python CLI”可以把两边的长处都拿到。

## 2. 项目事实

### 2.1 数据规模

- 正式模板 `物料编码申请单数据总模板.xlsx`：`B2:W40`，23 列、40 行，表头 4–5 行，数据从第 6 行开始；含合并单元格、边框、2 组数据验证（`C6:C19`、`E6:E19`）——数据验证只覆盖 6–19 行，模板却到 40 行，不能依赖 Excel 端下拉校验，后端必须重新校验。
- 简化示例 `inputExample-total.xlsx`：单行表头在第 3 行，数据从第 4 行开始；列数与正式模板不完全一致。
- 输出 TC：9 列，表头 1 行；`A11` 有一条“是否合法不填”的说明。
- 输出 Eplan：28 列，表头 1 行，示例数据 2 行。
- 结论：**数据量上限很小**（模板 40 行），性能不是选型因素；真正的复杂度在格式差异和业务规则。
- 本机已装 Qt 6.10.0 MinGW 64 + CMake，C++ 路线工具链是现成的；Python 3.12 + openpyxl/pandas 也可用。

### 2.2 处理逻辑

固定列映射 + 默认值 + 3 个必填校验（代号、部件编号、备注）+ 多文件合并 + 文本日志。没有复杂计算、没有大数据、没有并发要求。

### 2.3 原型现状

`transExcelFile.py` 已跑通“读总表 → 写 TC”的骨架，但：

- 用 pandas 新建工作簿，**没有套输出模板**，样式/列宽/表头格式不会保留；
- 只覆盖 TC，没有 Eplan、校验、多文件、日志；
- 行号/列号硬编码（`_row_init=6`、`_column_init=2`），换模板就失效；
- `while ... is not None` 遇到中间空行会提前停止；
- 全局 DataFrame 不重置，连续运行会串数据；
- 输出表头写的是 `ERP编码`，而 TC 模板是 `EPR编码`，设计文档又写“ERP编码（不填）”，三处不一致。

## 3. 关键维度对比

### 3.1 Excel 读写能力

| 能力 | Python（openpyxl/xlrd） | C++（QXlsx/OpenXLSX） |
|---|---|---|
| .xlsx 读写 | 成熟 | 可用，QXlsx 较成熟 |
| .xls 读取 | `xlrd` 免费成熟 | 基本没有免费成熟方案；libxl 商业、Excel COM 依赖 Excel |
| .xlsm/宏 | `keep_vba=True` 可保留 | 支持有限 |
| 样式/合并/数据验证 | 支持较好 | 支持，但细节和覆盖度不如 openpyxl |
| 模板套用 | `load_workbook` 后改单元格再保存 | QXlsx 可读写，但复杂模板易丢特性 |
| 公式/缓存值 | `data_only=True` 读缓存值；无缓存时为 None | 可读公式/值，需自行处理 |

**判断：** 如果输入可能是 `.xls`，Python 几乎直接胜出；如果严格只收 `.xlsx`，两者都能做，但 openpyxl 更省心。

### 3.2 性能

本机实测（Python 3.12 + openpyxl 3.1.5，`read_only=True`，Windows）：

| 行数 × 22 列 | 写入 | 读取 | 文件大小 |
|---|---|---|---|
| 1,000 | 0.18 s | 0.17 s | 82 KB |
| 5,000 | 0.71 s | 0.82 s | 392 KB |
| 10,000 | 1.45 s | 1.55 s | 778 KB |

模板只有 40 行，实际可能几百到几千行；**Python 的耗时在 1 秒量级，用户无感**。C++ 会更快，但快在这里不是卖点；为这点性能差距付出的开发和部署成本不划算。

### 3.3 部署

| 项目 | Python CLI（PyInstaller/Nuitka） | C++/Qt（QXlsx） |
|---|---|---|
| 产物 | 约 50–80 MB（onedir）或 30–50 MB（onefile） | 约 25–40 MB（静态 Qt） |
| 启动 | 0.5–2 s（onefile 更慢） | < 1 s |
| 目标机依赖 | 无 Python 环境也可运行 | 无 |
| 杀毒/白名单 | onefile 较容易被误报；签名可缓解 | 原生 exe 更稳 |
| 构建 | PyInstaller 简单；Nuitka 更稳但配置多 | Qt + QXlsx 构建链，CMake/qmake |
| 版本管理 | UI 与后端两个产物，需版本对齐 | 单产物，简单 |

**判断：** 部署是 C++ 唯一明显优势。若目标机是少量办公电脑、允许运行签名的打包 exe，Python 的部署成本可接受；若是上千台、IT 白名单只放原生程序，C++ 更稳。

### 3.4 开发与维护

- 粗略估计：同样功能，Python 核心约 600–900 行；C++/Qt + QXlsx 约 1,800–2,500 行（含错误处理、日志、JSON、测试）。
- 表头归一化、别名、默认值、校验规则这类“字符串和业务规则”代码，Python 的表达力和迭代速度明显更好；模板一变，改配置/改几行即可。
- C++ 的优势是类型安全、单进程调试、单产物；代价是每次调整都要重新编译，QXlsx 的边界问题需要自己踩。
- 这个工具大概率会随着业务调整映射和校验规则；**可维护性比微秒级性能重要**。

### 3.5 UI 集成与稳定性

- **独立 CLI + QProcess**：UI 不阻塞；解析崩溃不会带崩界面；可取消（kill 进程）；CLI 可单独跑、可自动化测试；代价是 IPC 和两个产物，但数据量小，IPC 开销可忽略。
- **嵌入 Python（pybind11）**：单进程、调用直接，但要处理 Python 运行时打包、GIL、异常跨语言传播、崩溃耦合；对这个项目是负收益。
- **PySide6**：没有 IPC，代码最少；但界面语言变成 Python，且打包体积更大。若你不坚持 C++ 写 UI，这是总成本最低的方案。

### 3.6 许可

- openpyxl：MIT；pandas：BSD；PySide6：LGPL；PyQt6：GPL/商业；Qt：LGPL/商业；QXlsx：MIT；OpenXLSX：MIT；libxl：商业。
- 闭源分发时，LGPL 的动态链接、版权声明、可替换库等义务要满足；PyInstaller onedir 比 onefile 更容易合规。具体让法务确认，这里只提示。

## 4. 推荐方案 A：Qt/C++ 壳 + Python CLI 核心

### 4.1 架构

```text
┌─────────────────────────────┐
│ Qt/C++ UI (Widgets)         │
│ 文件选择 / 进度 / 日志 / 取消 │
└──────────────┬──────────────┘

               │ stdout: JSONL 进度

┌─────────────────────────────┐

```

### 4.3 进程契约

`job.json`：

```json
{
  "job_id": "20261109-150000-abc",
  "inputs": ["C:/data/a.xlsx", "C:/data/b.xlsx"],
  "output_dir": "C:/data/out",
  "options": {
    "export_tc": true,
    "export_eplan": true,
    "on_invalid": "abort",
    "strict_headers": true
  }
}
```

`stdout` 每行一个 JSON（UTF-8）：

```json
{"type":"progress","stage":"read","file":"a.xlsx","current":1,"total":2}
{"type":"log","level":"warning","file":"a.xlsx","row":12,"field":"备注","message":"为空"}
{"type":"result","ok":true,"outputs":{"tc":"...","eplan":"..."},"stats":{"rows":120,"tc":100,"eplan":80,"errors":3}}
```

退出码：`0` 成功；`2` 校验失败；`3` 输入/表头错误；`4` 输出失败；`5` 取消；`1` 未预期异常。

要点：

- 所有路径用绝对路径；UI 传 `QString`，Python 3 在 Windows 上按 Unicode 接收，中文路径没问题；显式设 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`。
- `QProcess::SeparateChannels`；按行缓冲解析 stdout；stderr 单独收集，崩溃时原样展示。
- Windows 下给 `QProcess` 加 `CREATE_NO_WINDOW`，避免弹黑框；不要用 `--noconsole` 构建后端，否则没有 stdout。
- 取消：UI 调 `kill()`；后端在写文件前检查 job 状态；已写出的临时文件清理。
- 结果落盘 `result.json` + `import_YYYYMMDD_HHMMSS.log`，不要只依赖 stdout；进程崩溃时 UI 仍能读日志。
- 输出先写 `.tmp.xlsx`，再 `os.replace` 原子替换；输出文件被 Excel 占用时给明确提示。

### 4.4 解析策略（比选型更影响成败）

- **按表头名映射，不按固定列号**。先把表头归一化：去空白/换行、全角括号转半角、去掉 `（非必填）`、`（只有电缆填写）`、`(厂家)`、`(kg)`、`（mm）`、`（型号）`、`（或工作电压范围）` 等后缀。
- 别名表：`代号`/`代号（型号）`、`部件编号`/`部件编号（厂家代号）`、`备注`/`备注 (厂家)`、`重量`/`重量(kg)`、`名称`/`名称1`、`ERP编码`/`EPR编码`、`尺寸-宽`/`宽` 等。
- 表头行探测：在前 10 行里找命中 required 表头最多的一行；支持单行/双行表头；合并单元格取左上角值；数据起始行 = 表头底 + 1，跳过全空行。
- 找不到必需列时，直接报“缺列”，并把实际读到的表头打印到日志，方便用户改模板。
- 数据区：从起始行扫到 `max_row`，不要遇到第一个空行就停；全空行跳过，关键字段部分为空则报错。
- 类型：代号/部件编号/ERP 编码按文本写入（`number_format='@'`），避免前导零丢失；重量/尺寸按数值写入，空尺寸默认 0；对以 `=`、`+`、`-`、`@` 开头的用户文本做转义，避免公式注入。

### 4.5 配置化

把映射、默认值、必填规则放到 `config.json`/`config.yaml`（或一个只读的 `config.py`）：

```yaml
defaults:
  物料类型: 电器外购件
  材质: 成品
  单位: 件
  一类产品: "1:电气工程"
  行业/子行业: "1:电气工程"
required: [代号, 部件编号, 备注]
```

业务改规则时不用改代码、不用重新打包；这对“模板固定但规则会微调”的工具很关键。

### 4.6 日志

- 文本日志用 `utf-8-sig`，Windows 记事本/Excel 打开中文不乱码。
- 每行包含：时间、级别、文件、sheet、行号、字段、值、规则、消息。
- 同时输出 `result.json` 的结构化错误，UI 可做表格/跳转。
- 默认策略建议：**先收集全部错误，再决定是否导出**；默认“有错误整批不导出”，提供“跳过错误行继续导出”的显式选项，避免静默丢数据。

### 4.7 测试与打包

- pytest：表头归一化/别名、必填校验、默认值、条件导出（EPLAN/新TC 勾选）、多文件合并、空行/缺列/中文路径/损坏文件。
- 黄金文件：样例输入 → 期望 TC/Eplan，用 openpyxl 比较单元格值/类型，不比较二进制。
- 打包：PyInstaller `--onedir` 优先（启动快、易排查、LGPL 合规更简单）；Nuitka 作为备选。把 `templates/` 作为 data 打进产物。
- 在**没有 Python 的干净 Windows 虚拟机**上验收；测试中文路径、长路径、只读目录、输出文件被占用、杀毒拦截。
- 代码签名能显著降低 SmartScreen/AV 误报；内部工具也值得做。

### 4.8 回退路径

先定 JSON 契约，再实现 Python。若将来部署环境逼着你上 C++，只换 `datatrans-core.exe` 为 QXlsx 版本，UI 不动。这是方案 A 相对“全 C++”最大的战略优势：**选型可逆**。

## 5. 什么时候选 C++

同时满足以下条件时，C++/QXlsx 更合适：

1. 交付必须是**单个原生 exe**，不能接受子进程/额外运行时；
2. 输入**只可能是 .xlsx**，不需要 .xls/.xlsm；
3. 目标机数量大、IT 白名单/杀毒严格，Python 打包 exe 难落地；
4. 团队 C++/Qt 明显强于 Python，且愿意承担 QXlsx 的边界问题。

如果只是“我想用 Qt/C++ 练手”，选 C++ 也完全合理；但要把 Excel 库的能力边界先验证（尤其是 .xls、样式、数据验证、日期/公式），不要等到做完 UI 才发现库不支持。

## 7. 需求确认结果

已确认（2026-11-09）：

1. **权威输入模板**：只按 `inputExample-total.xlsx` 的布局实现；`物料编码申请单数据总模板.xlsx` 不要求支持。
2. **文件格式**：只接收 `.xlsx`；`.xls`/`.xlsm` 不接收。
3. **TC 的 ERP/EPR 编码**：留空；TC 模板表头原文 `EPR编码` 保留，不修改拼写。
4. **Eplan 一类产品/行业**：固定填写 `1:电气工程`。

当前实现约定（仍可按业务调整）：

5. `物料编码`、`长描述`、`标准管理员`、`单位重量`、`截面积` 不参与映射，忽略。
6. Eplan 的 `描述` 列留空；`价格` 留空。
7. 默认“有错误整批不导出”；界面可勾选“跳过错误行继续导出”。TC 的 `是否合法` 留空。
8. 多文件按顺序合并；同一“代号 + 部件编号”只写警告，不自动去重。
9. 输出模板只保留第 1 行表头，删除 TC 的 `A11` 说明行和 Eplan 的示例数据行。
10. 目标机为 Windows 10/11 64 位内网环境；已用 PyInstaller onedir + windeployqt 打出约 33 MB 的离线 zip 并验证。

## 8. 对 `transExcelFile.py` 的处理建议

**保留：**

- `_transDict` 的“源列 → 目标列”思路；
- 表头名称和默认值；
- 读取/写出的整体流程。

**替换：**

- 硬编码 `_row_init/_column_init` → 表头探测 + 别名映射；
- `pandas.to_excel` → `openpyxl.load_workbook(模板)` + 写单元格；
- 全局 DataFrame → 每次 job 独立的数据类/列表；
- `while` 遇空行停止 → 扫到 `max_row`，跳过全空行；
- 只写 TC → 同时写 Eplan；
- 无校验/无日志 → 规则引擎 + 结构化日志。

**注意：**

- `data_only=True` 只读缓存值；如果用户用程序生成文件且没有缓存，公式单元格会是 `None`。要么提示“请用 Excel 另存”，要么 `data_only=False` 后仅对已知公式做处理。
- 输出 code 列设文本格式，防止 `00123` 变成 `123`。
- 用 `read_only=True` 读大文件，降低内存；需要样式时再普通模式。

## 9. 决策矩阵（示意）

权重可按项目调整；分数 1–5。

| 维度 | 权重 | Python CLI | C++/QXlsx | PySide6 |
|---|---:|---:|---:|---:|
| Excel 能力/格式兼容 | 25% | 5 | 3.5 | 5 |
| 开发效率/可维护 | 20% | 5 | 3 | 5 |
| 部署/分发 | 20% | 3 | 5 | 3.5 |
| 与 Qt/C++ 技术栈匹配 | 15% | 4 | 5 | 3 |
| 性能 | 10% | 4 | 5 | 4 |
| 测试/运维 | 5% | 5 | 3.5 | 4.5 |
| 生态/长期风险 | 5% | 5 | 3.5 | 5 |
| **加权** | 100% | **4.35** | **4.08** | **4.28** |

解读：Python 方案领先，但不是压倒性；**部署是 C++ 唯一明显优势**。如果“单文件原生 exe”是硬约束，C++ 的权重会反超；如果界面不强制 C++，PySide6 几乎与方案 A 持平且更简单。

## 10. 最终建议

- **默认选方案 A：Qt/C++ UI + Python CLI 后端。** 你保留 Qt 前端，Excel 用 openpyxl，打包用 PyInstaller/Nuitka；JSON 契约让未来换 C++ 成为可能。
- 如果你不介意用 PySide6 写界面，**方案 C 更省事**：没有 IPC、没有两个产物、调试更直接。
- **不要**为了“纯 C++”而选 QXlsx，除非你已经确认它覆盖你的模板特性（尤其是 .xls、样式、数据验证）；也不要为了“用 Python”而把解释器嵌进 C++。
- 先做 1–2 天的 Python CLI 纵向切片（单文件 → 两个输出 + 日志），用真实模板验收；这一步会暴露 80% 的格式问题，再决定是否值得换 C++。
